# Budget guard correction interface — v1

Applies to the first B2G correction after independent review of8edc79b. Preserve the approved PostgreSQL ledger004, stages, provider prices and app architecture. This freezes missing interfaces; it does not approve the implementation or paid use. The guard currently has only test callers (`tests/test_v03_budget.py`, `tests/v03_budget_helpers.py`); no production adapter imports it. Update those tests to cross the supported interface below; retain all original G1–G6 behaviors and add meaningful independent-review regressions. No production domain/worker/schema change is authorized here.

## Transaction ownership

Expose `BudgetGuard(identity: BudgetIdentity)` in `app.budget`. It uses the existing production `db.connection` factory, never a caller's open connection. Every mutating public method opens its own bounded transaction, locks/checks/updates, commits before returning, and holds no locks over provider I/O. For invalid returned usage, persist uncertainty/known debt/pause in that transaction, exit the connection successfully, then raise the typed usage error. Failure to commit returns no send grant or successful settlement; caller must treat it as ambiguous. Never commit unrelated caller work.

Supported methods retain the existing operation/result names with `conn` and `account_id` removed (identity supplies the account). `reserve` and reconciliation have the explicit replacements below. `init_test_account` remains an explicit fixture utility restricted to test rows, not a paid bootstrap. Existing connection-taking mutation routines become private implementation helpers and must not remain a supported alternate path around identity, transactions or lifecycle checks. Tests exercise the same public methods as the future transport. Pure cost/quote helpers remain available but enforce pinned validated prices/context; no negative/zero/custom-price escape hatch.

## Required identity

`BudgetIdentity` is frozen and requires: `database_name`, `account_id`, `ledger_instance_id`, `environment`, `source_ledger_sha256`, `owner_cap_usd`, `opening_settled_usd`, `opening_uncertain_usd`. No permissive defaults. Every mutation checks `current_database()`, schema_migrations version4, and all expected persisted account fields under the account lock, before changing financial state or returning send authorization. Unknown/missing/mismatched identity fails closed. The configured identity comes from private server configuration, never browser/request input.

Test rows use explicitly constructed test identities and fixture amounts; test identity cannot select a paid row. Paid identity must match the authorized canonical source hash/opening amounts/cap30; this correction must not create a paid account, access a credential or enable a transport. Test fixture initialization remains explicit. Future paid account setup is a separately reviewed integration step.

## Request admission

`reserve(lease, unit, request_bytes, bound: RequestBound, attempt=0) -> ReservationResult` derives the conservative reservation itself. Remove caller-supplied `reserved_usd`. `RequestBound` is frozen, with exact fields `request_sha256`, `counted_request_sha256`, `model_id`, `pricing_version`, `input_tokens`, `max_output_tokens`, `context_limit`, `count_method`, `count_verified`. Model/pricing/context must equal pinned Spark1.3 constants; count_method is `count_endpoint`; count_verified must be exactly True. Counts are strict bounded integers, input/output positive, input+output <=1048576. Compute SHA256 of the supplied immutable canonical bytes and require both hashes to match it. Derive quote using pinned uncached input/output prices, fixed10% input margin and upward rounding. No automatic full-context shortcut in this correction; unverified media count blocks. Count provenance can be a labeled deterministic external-boundary double in tests; actual endpoint invocation and canonical rendering belong to later transport review.

Parse request_bytes as a JSON object without executing content. Require its actual `model` to equal the pinned model and its actual strict-integer `max_output_tokens` to equal the bound. Reject malformed JSON or a mismatched request parameter before admission; matching hashes alone cannot make a false output bound safe. Do not persist request_bytes or arbitrary caller dictionaries. Persist only validated bounded financial/request metadata. Exact canonical request serialization is owned by the future producer; tests supply deterministic JSON byte fixtures containing those actual model/output fields. This guard checks exact-byte/hash/count/parameter association, not the truth of an unexecuted external count endpoint.

Validate the actual stored analysis job's kind/video/run/generation/status/unexpired lease and the associated nondeleted video/run. The lease must match that complete tuple; caller `kind` cannot turn an analysis reservation into deletion authority. No first-run fallback. Bind the tuple, stage, request hashes, count/model/price basis and derived quote immutably. Same-unit replay returns the original result only for identical immutable inputs; changed basis/tuple/stage/request is Conflict. A valid retry is at most ordinal1 and has the same immutable request/stage/basis.

## Send and recovery gates

Preserve the original video→job→account/stage→attempt lock order when domain rows are involved. Financial-only receipt/settlement operations use account→attempt and never acquire domain locks afterward. Recovery scans of other jobs must not introduce account→other-job lock inversion; inspect their actual persisted lifecycle without taking conflicting domain locks. Admission and dispatch both serialize the account/stage gates, verifying identity, pause and closure; dispatch also rechecks the complete lease tuple. Return granted=True only after the first dispatched marker commits. Never grant again for that attempt after any terminal/received/dispatched transition, even after restart. Fail closed if a commit result is unknown.

On admission/dispatch, reconcile unresolved dispatched/received rows with their actual stored job identities. Missing/deleted job, generation mismatch or expired lease is stale unresolved debt: preserve the largest known exposure and pause admissions. Do not classify valid current in-flight jobs as stale, refund on expiry, or infer that a crashed sender was uncharged. A persisted received result can be settled/recovered without another send; stale financial recovery cannot publish deleted content. Reserved-but-unsent cancellation remains distinct. No production scheduler rewrite is needed.

## Receipts, settlement and reconciliation

Receipt identity is immutable. `record_receipt`, `settle`, rejection, uncertainty and cancellation must distinguish exact replay from conflicting input. Settlement cannot replace an already received hash, and an identical hash with different usage/evidence is a conflict. Preserve a bounded canonical fingerprint of validated settlement inputs in existing billing JSON if needed; no schema change.

Canonical usage requires strict integer input/cached/output/reasoning counts; cached<=input and reasoning<=output. A supplied total must be a strict integer equal to input+output. Validate maxima before Decimal/storage arithmetic; malformed, excessive, missing required or inconsistent usage takes the durable uncertainty path. Over-bound usage retains max(reservation, known actual charge), even above cap. Never store raw exception values or private text in errors. Missing optional provider usage must be normalized explicitly by the later transport from documented semantics, not silently validated here.

Repeated uncertainty preserves the maximum known charge and existing receipt/evidence. A lower or omitted partial charge cannot erase debt; conflicting receipt identity is rejected. New unresolved uncertainty pauses admission/dispatch; carried historical opening uncertainty remains included without falsely pausing the owner's new grant.

Replace boolean pause clearing with `reconcile_account(evidence: ReconciliationEvidence) -> AccountStatus`. This frozen type has a nonempty `resolutions` tuple; each resolution has `attempt_id`, `request_sha256`, `receipt_sha256`, canonical `usage` and validated scalar `billing_receipt`. Evidence must identify specific existing uncertain attempts, their immutable request/receipt identities and validated usage supporting the proposed settled result; it must reference an already durably recorded receipt. Reuse settlement validation and persist bounded resolution evidence. Empty/unrelated evidence is rejected; unresolved or receipt-less dispatched debt stays paused. There is no general `clear_pause` switch, guessed zero-charge resolution or automatic refund. Clear the pause only in the same committed transaction that resolves all newly uncertain/stale debt. A future manual provider-billing resolution without an existing receipt needs a separate authorized contract; do not invent an endpoint or billing proof.

## Explicit uncharged rejection

Retain `record_rejection` but require a typed bounded evidence object instead of free-form error_code: actual request identity, response hash, HTTP status and normalized rejection category. Allowed known-uncharged categories are rate-limit429, validation400, permission403 and account-denied; exact status/category association is validated. Only known uncharged429 may retry, with a required positive bounded Retry-After delay persisted before scheduling. Permission/account denials block further task execution. Timeout/5xx/unclassified outcomes go to uncertainty and cannot free reservation. Exact repeat is idempotent; changed evidence conflicts. The real classification producer executes in the later controlled transport review; test evidence is explicitly synthetic.

## Financial privacy

All surviving metadata, including bound_basis and alternate transition writers, uses explicit scalar field allowlists, strict types and bounded values. IDs/digests/enums/counts/money only; no note strings, nested caller objects, prompts, transcripts, raw request/response data or raw exception details. Reject unknown/content-bearing fields rather than quietly preserving them. Existing schema JSON columns can hold these validated fields; no new content FK. Domain deletion retains only this minimal debt/evidence, never media or participant text.
